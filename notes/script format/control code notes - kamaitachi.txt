According to a dump of the game's Huffman tree, there are around 0x62 control
codes in Kamaitachi from 0x1000 to 0x1061. Corroborating the 0x62 figure is
some code at $009585. If the game has determined a character in the uncompressed
character buffer is a control code, it will not run the code if the value is
0x63 or higher.

- what assembly code to execute for each at specific moments

Oddly, the table is about twice as large as it should be, with 0xC4 structures
instead of just 0x62 structures. Any purpose for the last half of the table?

Byte 01: Encodes how the game knows whether to read data as either regular
         Huffman codes or as Huffman pointers. There are two cases:
- For choice codes ($009AAB):
  * Bits 0-1 encode both (# Huffman codes - 3) and (# pointers - 2).
    For example, binary 10 -> 5 arguments and 4 pointers.
- For non-choice codes ($009ADE):
  * Bits 0-1 are # arguments.
  * Bits 2-4 are argument types (0 = Huffman codes, 1 = pointers).
  * Bits 5-6 unused?
  * Bit 7 = need to stop reading upcoming text if 1; keep going if 0 ($009A3E)
    Applicable codes: 1002, 1015, 1018, 101B-101F, 1024, 1025, 1027, 1029, 1037,
                      103A, 103B, 1040, 1041, 1043, 1045, 1048, 1049, 1050-62.
    Auto adv, end choice, end game, names, new chapter, clear, img fade in 27/29,
    gfx top layer, vfx, execute function, starting sfx, choices, punctuation
Also check:
- $00A2DA: skip control codes when encountering a NEW CHAPTER code
- $00A7E1: similar to above, don't know when each is called
- $00A87D: (context: got a skip choice text code) skip running control code if

What do the individual lists mean? How does the game know which to use?
With execute break points, I determined:
- $9D39 column is for, when you press X, the game must read up to ten pages back
  and assemble a data table at $0700 for each page (text ptr, prog flags, etc).
- $9D59 column handles ctrl codes in upcoming text that game reads in advance.
- $9D79 column handles ctrl codes when printing previously viewed text (X/Y buttons).
  * Method: check $009F61 for printing a name
- $9D99 column is for printing the chars on the chapter list screen.
  * Method: check $009F3F for the punctuation codes
- Hypothesis: $9DB9 column is for demo play or choice text? Check in game

For convenience, $009BBE = read pointer, $009B06 = read Huffman code.

Related, the "read previous text" feature that uses the $9D39 column has a limit
of 0x200 bytes per screen of text, since the text buffer starts at $0500 in RAM.
When playtesting, I found that screens of English text would exceed this limit
and clobber the table's contents, so I made an ASM hack to push it to $0800 (see
ASM @ $009E7D for creating the table, $04A121 for reading from the table).

Notes for how to read pointer data:

First pointer read upon bootup is at $05FD12-8. The state of the Huffman buffer 
is 0x01C0 (actual data is 0x00C0). The current script position (to next word to
read) is $05FD14. A hex editor at 0x2FD12 has the data [2D C0 01 00 67 03].

$0B = huffman buffer (with top 1 indicating end of data)
$0D = next two bytes from script data
$0F = either 1 if 8+ bits in Huffman buffer, or next two bytes after that if <=7

Here, WRAM data is [C0 01 01 00 01 00], or [01C0 0001 0001] in big endian pairs.

For first pair 01C0, rotate in a 1 at LSB and keep shifting left until you rotate
out the "end of data" MSB of 1.

So 01C0 -> 0381 -> 0702 -> 0E04 -> 1C08 -> 3810 -> 7020 -> E040 -> C080, done.
Data is now [C080 0001 0001], or as one big value, 00010001C080

Rotate in a 1 at MSB of big value, 0001 -> 8000. Make carries fall through to
get value of 80008000E040.
Keep shifting value right until you shift out the 1 that had been originally
rotated in at the LSB of 01C0 (the 038*1*). Final result should be 0100010001C0,
or as stored in memory: [C0 01 00 01 00 01].

Next, rearrange the data here into this state ("--" = a [00] byte):
Original:  0B 0C 0D 0E 0F 10
Rearrange: 0E 0F 0B 0C 0D --
Data:     [C0 01 00 01 00 01]
New data: [01 00 C0 01 00 --]

With data in this state, call $009C18 to get the final data for Huffman pointer.

X <- value in $0E-$0F, [01 00] or 0x0001.
Bitwise AND the value $0E-$0F with 0x03FF.
Take original value of $0E-$0F, and bitwise AND with 0xFC00 (the other 6 bits).
Left shift this, and OR these bits into memory at $0E-$0F.

To summarize, let N = $0E-$0F.
N <- (N & 0x03FF) | ( (N & 0x7C00) << 1)
Result should be 0x0001, unchanged in this case.

Descriptions of control codes' functions:

Codes that do not have Huffman encodings for the script:
- 1009-100C, 1013, 1014, 1026, 1038, 1039, 1045, 1049-104C, 1057, 105F

1000 = delay code, with one argument that encodes multiples of 10 frames
to pause the script engine by.

1001 = delay code, inserted after commas; directly encodes # frames

1002 = auto advance text when there would normally be a WAIT

1003-100C are control codes to set the text speed. Each uses a constant value to
set a memory address that says "wait N frames until getting next character from
script and printing it to the screen."
- 1004: normal speed, 1 frame per character
- 1005-1008 each use  2,  3,  4, or 12 frames per character. (all used)
- 1009-100C each use 24, 36, 48, or 60 frames per character. (all unused)
  Repurpose them for text kerning?
- 1003 is a special case that sets the variable as 0, which more or less means
  "print as much as possible per frame." Usually, the text speed is about 3 or 4
  characters per frame. If the game is doing visual effects like snow, it slows
  down quite a bit. Mainly used for printing previously read text, but is also
  used once in the script for the end of the karaoke joke segment.

100D = wait for player input
100E = line break

---

100F = script position jump

1010 and 1011 are conditional script position jumps; check progress flag to know
if to take or not. 1010 takes it if a flag is SET. 1011 takes it if flag CLEAR.
More about these flags at the bottom.

1012 = conditional script position jump (checks temporary flag that gets reset
       if the player decides to jump back to a point before the flag gets set)

1013 = not used in the script, but I found that it should be like 1012, but only
       takes the jump if the temporary flag is clear.

---

1015: marks "end of text for choice option"
1016: Indicates that the text printed for a choice is different from the text
      that appears when you actually pick it. Ignore chars until finding a 1015.

---

1017: Its ASM code consists only of running BRK_1C(29). See $00B48E, $049DDD

It only pops up right before points where the player can potentially loop back
to where they currently are. Excluding the maze section, the JP game has three
such points: first opportunity to announce the killer's identity (input 0001),
the second opportunity (input 0002), and "let me see the note again" in the
treasure route (input 0004). Why no input of 0003?

Purpose seemingly to prevent having to store infinite copies of pointers to the
repeated text in the save file? Once the loop completes, you aren't able to view
the text that you just read during the loop. For example, if you say "It was
Mari" at the first opportunity, you won't be able to view the text from the
aforementioned path once you get back to the choice.

---

1018 marks endings, both good and bad. Text decompression will stop with it.

---

1019 sets the X position of text on screen.
101A is similar for the Y position.

---

101B = Protag's name
101C = Girlfriend's name

101D, 101E and 101F are all similar.
At three specific points in the murder mystery route, the game will make you
enter, in hiragana, the name of who you believe to be the killer. When you make
your choice, this code will print the person's "canonical" name in kanji (if it
matches with someone in the game's story) or the verbatim hiragana name (if no
match found).

There is, in fact, a purpose to having three control codes here for killer
guesses. When going through the script, it is possible to reach two or more of
these "enter the killer's name" points, and guess wrong with at least one.
Should the player decide to read back in the script with the chapter list (press
R or Select in gameplay), the engine must print the player's guesses at the
correct points. By extension, all three guesses must be kept track of.

This presents several problems with creating an English patch, because most
characters' names (either first or last) are longer than 6 characters.
- How to modify the name entry screen ASM code to handle, say, 10 characters?
- How much ASM is separate for naming Tooru/Mari and for naming the killer?
- Is there enough room in the memory map to hold 10 characters?
- How to modify the SRAM format to handle five sets of 10 characters?

Would it be sufficient to try changing the ASM to use a one-byte encoding
instead, specifically for storing the names?

1020 sets a progress flag in the save file. They get checked for 1010 and 1011.
    The input value is comprised of a four-bit value and a three-bit value:
    0 XXXX YYY, where XXXX is the byte offset from address 0x10 in SRAM,
    and YYY is the offset in ROM from $018B65 for the bit pattern to set.
    The bit patterns are, unsurprisingly: 01 02 04 08 10 20 40 80
    The flags for the current playthrough are stored at $700010.
    The flags for all playthroughs so far are stored at $700018.

1021 only appears twice in the script, in pink bookmark text.
    According to the assembly code at $00AF1F, it resets progress flags.
    It is for limiting access to a secret message in the game.

1022 sets a "temporary" progress flag that gets cleared should the player choose
to start over the beginning, or start from a chapter before the flag got set.
However, it will otherwise persist for the rest of the current playthrough.

1023 clears one of these temporary flags.

102B-1036: Silhouette control codes.
These have one "main" input that identifies what silhouette graphics to load.
Chunsoft programmed these to have the 0x100's place of the silhouette ID value
to be baked into the control codes themselves, as in "take input and add 0x100
or 0x200" or "just use input as-is."

Example:
1031: Load silhouette set 0x0__, e.g. <1031><$0040> loads set 040
1032: Load silhouette set 0x1__, e.g. <1032><$0040> loads set 140
1033: Load silhouette set 0x2__, e.g. <1033><$0040> loads set 240

I presume this was done in the interest of keeping the script's Huffman tree
smaller than having the full IDs like 140 encoded in the script. In fact, this
is beneficial to a translation patch that will likely use a much smaller set of
characters than Japanese.

103C-103E: These change the color components (B/G/R) for the silhouettes.
   They all come in triples. 103C is blue, 103D is green, 103E is red.
   Input is a 5-bit value for the color component.

Perhaps note that their default color in CGRAM is 04E7 (BGR components 1,7,7 or
RGB24 393908), which is like a green shade of brown. However, the color math*
going on under the hood typically makes it show up as shades of blue on screen.

*: According to the color math registers listed in Mesen's Register Viewer,
   colors are calculated as BG1 - SUB, where the subscreen is the sprite layer.

In effect, you can think of the inputs for these as "how much of the color
component should the silhouette block out from the background?" With the default
color, it reduces the background's red and green components but lets through the
blue component mostly unchanged.

Another example: In scenes in the basement with silhouettes, the inputs are
BGR 1F,0,1F. This completely blocks out the red and blue components and only
lets through the green component. Indeed, they show up as shades of green.

1050-1057 look to be choice codes.
  In both cases, once you pick a choice, the buffer "resets" back to $0500.
  There are two choice codes each for having 2, 3, 4, or 5 options.
  If N = # options, # of Huffman arguments is N+1, and # pointers is N.

  Based on the choice codes present in the script, the first Huffman argument
  uniquely identifies what choice it is.

  The other N, I decided to just ignore for a very long time, until I found out
  more about the SRAM format. Each choice has a byte in SRAM that tells which
  options have been picked by the player. The N arguments might refer to the bit
  position to set in the byte for each available option.

Control codes 1058-1061 are for placing punctuation characters into the text
buffer in memory. They may or may not have a WAIT and/or a LINE following them,
depending on whether the AUTO ADV flag was set, or if either flag indicating "in
dialogue" or "in quoted dialogue" is set.

The puncutation character itself is placed into the script buffer at $009F3F.
