$00A9BF: Bits 6-7 are flags about what bytes to modify in the range 0B94-0B97.
Ranges 00-3F -> 0b94, 40-7F -> 0b95, 80-bf -> 0b96, c0-ff -> 0b97.

0b95 range: 01-03 20 23 29 2a 2c 3c 3d 40 47-49
0b96 range: 13 1f 24 25
0b97 range: 21 32 4f
Some kind of way to prioritize which ones get run first?

$00ABAF: Input flag in C flag. Check value N in bits 0-1 (bits 2-5 unused):
N = 0? do nothing, regardless of C flag
N = 1 and carry CLEAR? do nothing

Otherwise, run the code at $00ABCC-$00ABEA.

Input 01 ("brownscale")

The game uses a lookup table at $5FE9DC for converting colors to "brownscale,"
if that makes sense. Like grayscale, but where the colors are shades of brown.

The formula for what index to use, given a color with 5-bit B/G/R components, is
X = (R*5 + G*0xA + B*2) >> 4. The ASM code uses right shift 3 and AND with FFFE.

VFX 02: While not used in the script, the ASM code seems to do like a color
inversion. However, instead of necessarily doing the inversion based on white
(BGR15 7FFF), it finds the strongest color component C in all of CGRAM (except
colors used for the text) and uses C*(B=1,G=1,R=1) as the basis.

--------------------

$03C4E6: $98,$9A,$9C contain the R/G/B components for a color value
Output values will be in $9E,$A0,$A2
$A2 will have the mean of the smallest and largest components

If R=G=B, $9E <- 0, $A0 <- 0, $A2 <- the component (still qualifies as mean)

Otherwise, sort them from greatest to smallest (big, middle, small)
Construct two 10-bit values consisting of the data:
X <- ((mid - small) << 5) | (big - small)
Y <- (big << 5) | small
Use these values as a byte offset into a list at $5FD99A (value range: 00-1F).
For the byte you get with the Y offset, store it directly to $A0.
For the byte you get with the X offset, you likely need to modify it ($9E).

(Assume below that a single two-way tie may occur, but not a three-way tie)
R>=B>=G: 0xC0 - value       B>=R>=G: 0x80 - value
R>=G>=B: value              G>=B>=R: value + 0x40
B>=G>=R: 0x40 - value       G>=R>=B: 0x80 - value

         the whole screen itself also shifts left/right

         until it is done, text prints on screen more slowly, and will not show
         next screen of text until color cycle is done

$03C7C0: cut out silhouettes, colors on screen become brighter

The code at $03D048 is not used in the script, but when I forced the game to
load it anyway as VFX code (change pointer for VFX ctrl code input in table),
it crashed the game in an interesting way.
- First, the graphics mode is set to Mode 7, assuming that any graphics data in
  VRAM is indeed in Mode 7 formatted tiles.
- Then, the game displays ten memory addresses on the right side of the screen,
  specifically the Mode 7 affine transformation values, M7HOFS/M7VOFS, and two
  other things I don't know yet.
- The hex digits for the addresses are, interestingly, sourced from a font that
  exists uncompressed at the very end of the ROM.
