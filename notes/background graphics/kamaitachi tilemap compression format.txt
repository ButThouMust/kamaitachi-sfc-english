Kamaitachi no Yoru compresses the tilemap data for background graphics in four
separate phases. The phases are based the encoding for two-byte tilemap entries:

FEDCBA98 76543210 -- y = Y flip, x = X flip, (priority bit assumed to be 0 here)
yx0pppnn nnnnnnnn -- ppp = palette #, nnnnnnnnnn = tile ID number to use

Phase 1: Read a block of data for the low byte of the tile ID numbers.
Phase 2: Read a block of data for the two high bits of the tile ID numbers.
Phase 3: Read a block of data for the palette numbers to use.
Phase 4: Read a block of data for the X/Y flip bits to use.

All tilemaps are assumed to be 0x20 tiles wide and 0x1C tiles tall.
In total, the full decompressed data should be 0x700 bytes.

The tilemap pointer for graphics ID 0x66 (bookmarks on the file select screen)
is a special case, pointing to TWO tilemap blocks. Purpose is so one bookmark
can be on top of the other two when it is selected.
$46C0AF: Just one bookmark. Pointer encoded as 4640AF (0x008000 bit clear).
$46C1B8: Layout of three bookmarks; middle one overlays the top and bottom ones.

--------------------------------------------------------------------------------

$028D47

Given a graphics ID number, you will get a pointer to the tilemap data from the
list at $258000-$258491. Seek to this pointer in the ROM, and read a byte.
The low 4 bits of this byte tell you if the data in each phase is compressed (1)
or not (0).

If the data for a phase is uncompressed, read a block of 0x380 sets of the "base
unit" for the current phase.
- Tile ID low bytes: just a block of 0x380 bytes.

- Tile ID high bits and X/Y flip bits: block of 0x380 2-bit units (0xE0 bytes).
  Specifically, they are consecutive like binary 00112233 44556677 etc.

- Palette bits: 0x380 groups of 3-bit units (0x150 bytes).
  Specifically, eight 3-bit units are grouped into three bytes, where the three
  bits at a specific bit position comprise a group.

All of the game's tilemap blocks are compressed. Perhaps the ASM code for the
uncompressed tilemap blocks was used during development.

Typically, the compression formats read a byte and examine the top couple bits
to know how to decompress data.

--------------------------------------------------------------------------------

If the tilemap low bytes are all uncompressed, you read 0x380 bytes from the ROM
directly into the decompression buffer. Otherwise...

Tilemap low bytes compression format:

Start the decompression with an initial tile ID of 001 (tile ID 000 is fully
transparent). Keep track of both the current tile ID, and how many tile ID
low bytes have been written to the buffer.

Read a byte from the ROM (referred to as "type byte" in this writeup).
The cases for how to decompress data:

00xx xxxx: $029B02 (Range 00 to 3F)
- Write a total of (typeByte + 2) copies of the current tile ID #. (02-41 times)
- Increment the current tile ID #.

01xx xxxx: $029B13 (Range 40 to 7F -- 7F is a special case)
- # bytes to write for this case is either:
  * (typeByte & 0x3F) if typeByte is not 0x7F
  * the next byte from the ROM, if typeByte is 0x7F
- Whatever value you have, increment it.
  * In other words, you can either write up to 0x40 bytes, or up to 0x100 bytes.
- Write a sequence of increasing tile IDs, starting from the current tile ID.
  For example, if the type byte is 44 and the current tile ID is 0xCD, you would
  write the 5 byte sequence: [CD CE CF D0 D1]. FF will roll over to 00.

100x xxxx: $029B33 (Range 80 to 9F)
- # bytes to write for this case is (typeByte & 0x1F) + 1.
- Read that many bytes from 0x20 bytes (one tile row) back in the decompression
  buffer, into the current position in the decompression buffer.

101x xxxx: $029B4F (Range A0 to BF)
- Take the most recently written low byte written in the decompression buffer.
- Repeat it a total of (typeByte & 0x1F) + 1 times.

110x xxxx: $029B63 (Range C0 to DF -- DF is a special case)
- If type byte is not 0xDF, use (typeByte & 0x1F).
- If type byte is 0xDF,     use the next byte from the ROM, MINUS ONE.
- The repeat count is this value, plus 2.
- Read a byte from the ROM and write it the specified number of times.

111x xxxx: $029B8B (Range E0 to FF)
- Read a total of [(typeByte & 0x1F) + 1] bytes from the ROM directly into the
  decompression buffer.

----------

A note about loops: For some reason, it is possible for the game to write a byte
or two over the 0x380 byte limit. I recommend you put in a check like "# bytes
written < 0x380" in addition to the loop counter checks.

--------------------------------------------------------------------------------

The sections on tile ID high bits and X/Y flip bits use a subroutine at $029EAA,
which uses a one-byte buffer containing four 2-bit values. Whenever it gets
called, it will return the topmost 2 bits in the buffer (provided there is at
least one bit pair left). I called it "get two bits from byte from pointer".

Pseudocode representation:
bitPairsLeft -= 1
if (bitPairsLeft < 0) {
    buffer <- next byte from ROM
    bitPairsLeft <- 3;
}
output <- buffer & 0xC0
buffer <- buffer << 2
return output

--------------------------------------------------------------------------------

$029BA3

If the block for tilemap ID high bits is uncompressed, read 0x380 sets of them
from the ROM (0x380 >> 2 = 0xE0 bytes) and write them to the decompression
buffer.

Read a type byte from the ROM.
The cases are:

00xx xxxx: $029BEA (Range 00 to 3F -- 0x3F is a special case)
- If type byte is not 0x3F, the repeat count is the type byte itself.
- If type byte is 0x3F,     the repeat count is the next byte from the ROM.
Use tile ID high bits of 0b00 for (repeat_count + 1) entries.

01?x xyyy: $029C06 and $029C11 converge at $029C1E (Range 40-5F and 60-7F)
- Two cases reuse code but get repeat count and initial 2 bit value differently.
  * ? bit is 0: use "yyy" bits as repeat count, and "x" bits as 2 bit value
  * ? bit is 1: use the whole "xxyyy" value, plus 8, as the repeat count,
                and the 2 bit value is from the "get two bits" subroutine.
- First, write the initial 2 bit value.
- Then, use 0b00 as tile ID high bits for the next (repeat count + 1) entries.

10?x xyyy: $029C30 and $029C3C converge at $029C49 (Range 80-9F and A0-BF)
- Similar, code reused, but get repeat count and a two bit value differently.
  * ? bit is 0: use "yyy" bits, plus 1, as repeat count; "xx" bits as 2 bit val
  * ? bit is 1: use the whole "xxyyy" value, plus 9, as the repeat count,
                and the 2 bit value is from the "get two bits" subroutine.
- Use the 2 bit value for the next (repeat count + 1) entries.

11xx yyyy: $029C56 (Range C0-FF)
- Take the "xx" bits, and write them as the top two bits for ONE tile ID #.
- Use the "yyyy" bits, and write that many 2 bit values from the "get two bits"
  subroutine.

Keep repeating this loop until you have written 0x380 sets of tile ID high bits.

--------------------------------------------------------------------------------

The section for palette numbers uses a subroutine at $029EC5 for grabbing three
bits of data at a time, from a three byte buffer from $1F0F-$1F11.

       76543210
$1F11: xxxxxxxx     If you imagine stacking them at left, you read out a column
$1F10: yyyyyyyy     of bits at a time, starting from bit column 7. The output is
$1F0F: zzzzzzzz     a byte in the format [000xyz00].

Whenever all three groups of 8 bits are exhausted, the game will read 3 bytes
from the ROM into the three byte buffer, in the order $1F0F, $1F10, and $1F11.

--------------------------------------------------------------------------------

$029C73

If the palette numbers are all stored uncompressed, the game will read 0x380
sets of three bits from the ROM using the "get palette number from $0F-$11"
subroutine. 0x380 sets of 3 bits -> 0xA80 bits -> 0x150 bytes.

Otherwise, keep reading type bytes until 0x380 sets of 3 bits have been read.

00xx xxxx: $029CC7 (Range 00-3F -- 0x3F is a special case)
- If type byte is not 0x3F, repeat count is the type byte itself.
- If type byte is 0x3F, repeat count is the next byte from the ROM.
Skip forward in decompression buffer by (repeatCount+1) bytes.
Note: $029CD6 is a common branch target that does "skip by repeatCount PLUS ONE
      bytes".

0100 xxxx: $029CE7 (Range 40-4F)
011p ppxx: $029CFC (Range 60-7F)
1010 xxxx: $029D06 (Range A0-AF)
- These three do the same thing in concept: write a single palette value, and
  skip by some number of bytes. However, each one calculates the skip size and
  gets the palette value differently.
- 0100 xxxx: Skip size = "xxxx" bits; palette from 0x20 bytes back = 1 tile up.
- 011p ppxx: Skip size = "xx"   bits; palette is in the "ppp" bits.
- 1010 xxxx: Skip size = "xxxx" bits, plus 4. Palette from "get palette val."
Pass in repeat count to $029DC6 as mentioned above.

0101 xxxx: $029D19 (Range 50-5F)
- Repeat count is the "xxxx" bits.
- Take a palette number from 0x20 bytes back, which is to say the tile directly
  above the one we are currently in. Copy it (repeat count + 1) times.

100p ppxx: $029D3E (Range 80-9F)
- Repeat count is the "xx" bits plus 1.
- Palette number is the "ppp" bits. Copy it a total of (repeat count + 1) times.

1011 xxxx: $029D49 (Range B0-BF)
- Repeat count is the "xxxx" bits plus 5.
- Take a palette number from the "get palette number" subroutine.
  Copy it a total of (repeat count + 1) times.

11pp pxxx: $029D65 (Range C0-FF)
- Repeat count is the "xxx" bits.
- Take the palette number encoded in the "ppp" bits, and copy it ONCE.
- Run the "get palette number" subroutine a total of (repeat count) times, and
  copy in the sequence of values you get.

--------------------------------------------------------------------------------

$029D86

Once you have filled in all the palette values, you have to propagate an XOR
operation throughout the high bytes of the tilemap.

Specifically, for every tile starting from tile row 1 (topmost is tile row 0):
- Get the high byte from the tile directly above it.
- XOR it into the high byte of the current tile.

for each tilePos where ONE_TILE_ROW <= tilePos < tilemapSize (go top to bottom):
    hiByte[tilePos] <- hiByte[tilePos] ^ hiByte[tilePos - ONE_TILE_ROW]

Which is to say, XORs propagate down the tile columns of the tilemap.

Why do this? It appears that this makes the high bits and palette indices
compress better than if you fed them into the compression algorithm as-is.

--------------------------------------------------------------------------------

$029D9B

If the X/Y flip bits are uncompressed, read 0x380 sets of them from the ROM
(0x380 >> 2 = 0xE0 bytes) and write them to the decompression buffer.

Otherwise, read type bytes from ROM until 0x380 sets of X/Y flip bits are read.

00nn nnnn: $029DE9 (Range 00-3F -- 0x3F is special case)
- If type byte is not 0x3F, skip (type_byte + 1) sets of flip bits, all 00.
- If type byte is 0x3F, read another byte N from ROM, and skip (N+1) bytes.

0100 nnnn: $029E09 (Range 40-4F)
- Get the X/Y flip bit set from the tile that is one row up (0x20 bytes back).
- Copy them into the current tile, and skip (N+1) bytes in buffer (0x1-0x10).

011y xnnn: $029E1C (Range 60-7F)
- Get the X/Y flip bit set from the "yx" bits in the type byte.
- Store them into the current tile, and skip (typeByte & 0x7) bytes in buffer.

1010 nnnn: $029E27 (Range A0-AF)
- Get the X/Y flip bit set from the "get two bits" subroutine.
- Store it into current tile. Skip (typeByte & 0xF) + 9 bytes in buffer.

0101 nnnn: $029E3C (Range 50-5F)
- Get the X/Y flip bit set from the tile that is one row up.
- Copy it into the next (repeat count + 1) tiles.

100y xnnn: $029E61 (Range 80-9F)
- Get the X/Y flip bits from the "yx" bits in the type byte.
- Copy them into the next ("nnn" bits + 2) bytes.

1011 nnnn: $029E6D (Range B0-BF)
- Get the X/Y flip bits from the "get two bits" subroutine.
- Repeat count is ("nnnn" bits + 0xA). Copy bits into that many bytes.

11yx nnnn: $029E8B (Range C0-FF)
- Get X/Y flip bits from the "yx" bits in the type byte. Copy it into ONE tile.
- For the next "nnnn" bytes, read two bits from the "get two bits" subroutine.

--------------------------------------------------------------------------------

All the bytes have been decompressed now. The final step for a dumper is to take
each pair of low and high bytes and interleave them together.

Some findings about the 131 tilemap data sets available in the Japanese ROM:
- Unfortunately, there is no one tilemap that runs through every single case for
  all four phases.
- The most you can get is covering all cases for low bytes, high bits, and
  palettes, but not all the cases for X/Y flipping.

Distribution of combinations (L = low, H = high, P = palette, F = flip):
none: 37  | LH  :  9  | LHP : 12
          | L P : 12  | LH F:  0    For just raw counts of each type:

How to implement a recompressor

Input data: a 0x700 byte block of 0x20*0x1C two-byte SNES-format tilemap entries
Output data: the data having been optionally compressed but always separated out
             into the four individual data blocks.

Recommendations:
- Split up the 0x700 bytes into the four blocks. Just use four arrays of 0x380
  values each, regardless of if the unit occupies the whole byte or not.
- Make a dedicated function for checking each case, that given a position to
  start searching from, outputs # units that get compressed under that case.

As for preparing high bits and palettes for the decompression's XOR propagation,
you will want to start at the bottom row and do row[N] <- row[N] ^ row[N-1].
That is, XORs from bottom-up in compression undo XORs from top-down in decomp.

Let's go over the compression formats again and examine what each case is
designed to do in terms of compression.

--------------------------------------------------------------------------------

Tilemap low bytes compression format:

Things to keep track of:
- The current tile ID value (starts at 001)
- The current position in the decompression buffer

00xx xxxx: $029B02 (Range 00 to 3F)
Purpose: compress 02-41 contiguous copies of the current tile ID # into 1 byte
Encode (size-2) in type byte - note that min size for this case is 2 bytes!
Increment the current tile ID #.

01xx xxxx: $029B13 (Range 40 to 7F -- 7F is a special case)
Purpose: compress 0x01-0x100 bytes that monotonically increase by 1 each time,
         starting from the current tile ID #
Check the size of the group.
If size <= 0x3F bytes, encode (size-1) in type byte
If size > 0x3F bytes,  encode type byte of 0x7F, and then (size-1) in type byte
Add the size of the block, PLUS ONE, to the current tile ID #.

100x xxxx: $029B33 (Range 80 to 9F)
Purpose: reuse a block of at most 0x20 bytes starting from 0x20 bytes back in
         decompression buffer; note that this checks for matches byte-by-byte
Encode (size-1) in type byte

101x xxxx: $029B4F (Range A0 to BF)
Purpose: reuse the most recently written low byte from decompression buffer,
         up to 0x20 times
Encode (size-1) in type byte

110x xxxx: $029B63 (Range C0 to DF -- DF is a special case)
Purpose: a byte repeats 2+ times (up to 0x100) but is not the current tile ID
- If 0x2 <= size <= 0x20, encode (size - 2) in the type byte's x bits.
- If size > 0x20, use a type byte of 0xDF, and encode (size - 1) in next byte.
After encoding the size either way, write the byte that is to be repeated.

111x xxxx: $029B8B (Range E0 to FF)
Purpose: Byte sequence appears that does not fit under any of the other cases
Insight: You can't apply any compression case to any one byte in this sequence 
- Group together anywhere from 0x1 to 0x20 bytes at a time.
- Encode (size-1) in type byte, then write the byte sequence itself.

--------------------

A table summarizing this compression format:

 case  | size range | # bytes  | description
-------+------------+----------+------------------------
 00-3F | 0x 2-0x 41 |     1    | repeat current tile ID
-------+------------+----------+------------------------
 40-7E | 0x 1-0x 3F |     1    | write increasing byte
    7F | 0x40-0x100 |     2    | seq. starting @ curr ID
-------+------------+----------+------------------------
 80-9F | 0x 1-0x 20 |     1    | reuse from one row up
-------+------------+----------+------------------------
 A0-BF | 0x 1-0x 20 |     1    | reuse most recent byte
-------+------------+----------+------------------------
 C0-DE | 0x 2-0x 20 |     2    | repeat a new low byte
    DF | 0x21-0x100 |     3    | value from the ROM
-------+------------+----------+------------------------
 E0-FF | 0x 1-0x 20 | 0x2-0x21 | sequence of literals

--------------------

Based on some sets of these compressed low bytes in the ROM, Chunsoft's original
compressor had some special cases for handling certain match patterns:

- Sequences like [00 01 02 02 02] should be grouped like [00 01] [02 02 02], not
  like [00 01 02] [02 02]. Limit the increasing sequence to use the "repeat
  current tile ID" case instead of the "repeat most recent byte" case. The key
  difference is that [00 01 02] will set the current tile ID to 03, not 02.
  Plus, the "repeat current ID" case can compress more data with a single type
  byte than the "repeat most recent value" case.

- Chunsoft's compressor seemed to prioritize reusing data whenever possible,
  preferring a [reuse from 1 row up] and [repeat most recent byte] combination
  if available, over a [repeat new value N times] if the "new" value happens to
  match the one from a tile row up.

Optimizations I found out when making a recompressor:
- Say that you find a long run (0x41+) of the current tile ID:
      | enc. |
total | size | best case
------+------+----------------
    1 |  1   | L=01 inc. seq.
 2-41 |  1   | repeat curr ID
42-61 |  2   | L=41 repeat curr ID, rest w/ reuse most recent or row up
62-81 |  3   | - L=41 repeat curr ID, L=20 reuse, rest reuse
      |  3   | - repeat new ID
82-100|  3   | repeat new ID

Notice how a length of 42-61 would be encoded in 3 bytes if you used the "repeat
new ID" case for its whole length (and wouldn't increment the current ID value),
but in only 2 if you used the strategy that's described in the table above.

--------------------

There's one fairly specific special case for the tilemap at $47F675 (gfx ID 79)
where my typical detection for increasing sequences was worse by two bytes.
Data block @ offset 241-249: [19 1b 00 00 00 00 00 19 1a]; current tile ID = 19.
Typical detection encoded it as:    Chunsoft's picked up that it's better to do:
(1) 1 byte increasing sequence      (3) 2 literals
(2) 1 literal                           -
(1) [5 bytes from row up]           (1) [5 bytes from row up]
(2) 1 literal                       (1) 2 byte increasing sequence
(1) 1 byte increasing sequence          -

My solution for trying to detect this case in a generalized way both worked on
the specific case above, and even managed to find a few more instances of it. It
saved another 9 bytes across the game's data.

Assume that an increasing sequence is 1 byte long. Look for the next occurrence
of the current tile ID in the low bytes (quit if on the way, you find the next
value for the current tile ID were you to take the 1 byte increasing sequence).
If the increasing sequence at the next occurrence is strictly longer than 1,
forgo the 1 byte increasing sequence for now, and encode as next best case.

--------------------------------------------------------------------------------

Tilemap ID high bits compression

Need to keep track of:
- Buffer for non-zero high bit values
- How many positions (0 to 3) are filled
- When should the high bits buffer be written to the compressed data buffer?
  And, how many buffers should be written?

00xx xxxx: $029BEA (Range 00 to 3F -- 0x3F is a special case)
Purpose: Use high bits of 00, up to 0x100 times.
How many times?
- If size <= 0x3F, encode (size-1) in the type byte as xxxxxx bits.
- Otherwise, use a type byte of 0x3F, and another byte for (size-1).

01?x xyyy: $029C06 and $029C11 converge at $029C1E (Range 40-5F and 60-7F)
Purpose: One non-zero high bit value; up to 0x27 sets of high bits 00 after.
How many 00s after? Use 010x xyyy for under 8, and 011x xyyy for 8 or more.
- If size <= 0x7, encode size in type byte as yyy bits, and non-zero val as xx.
- If size >= 0x8, encode (size-8) in type byte as xxyyy bits.
  Encode non-zero value in the high bits buffer.

10?x xyyy: $029C30 and $029C3C converge at $029C49 (Range 80-9F and A0-BF)
Purpose: Repeat the same non-zero high bit value multiple times.
Let N = repeat count (size). Use 100x xyyy for 1 to 8, and 101x xyyy for 9+.
- If 0x2 <= N <= 0x9, encode (N-2) as yyy bits, and value as xx bits.
- If 0xA <= N <= 0x29, encode (N-0xA) as xxyyy bits. Encode value in buffer.

11xx yyyy: $029C56 (Range C0-FF)
Purpose: Several (0x1 to 0x10) literal values for the top bits.
         Note that high bits of 00 can be encoded in this case.
Encode the FIRST of these literal values in the xx bits of the type byte.
Encode (size-1) as the yyyy bits in the type byte. (Note that this may be 0x0)
Encode the other (size-1) high bit values in the buffer.

--------------------

A table summarizing this compression format:

 case  | size range | # bytes  | # buf. vals | description
-------+------------+----------+-------------|-------------------------
 00-3E | 0x 1-0x 3F |    1     |      0      | Run of all 00 high bit
    3F | 0x40-0x100 |    2     |      0      | values (up to 0x100)
-------+------------+----------+-------------+-------------------------
 40-5F | 0x 1-0x  8 |    1     |      0      | Single non-zero high bit
 60-7F | 0x 9-0x 28 |    1     |      1      | then up to 0x28 00 vals
-------+------------+----------+-------------+-------------------------
 80-9F | 0x 2-0x  9 |    1     |      0      | Repeat same non-zero val
 A0-BF | 0x A-0x 29 |    1     |      1      | up to 0x29 times
-------+------------+----------+-------------+-------------------------
 C0-FF | 0x 1-0x 10 |    1     |   0x0-0xF   | Sequence of literals

Perhaps note the lack of a "reuse from one row up" compression case here.

Also note, the literal sequence case can make you have to read multiple bytes of
high bit sets from the ROM. This also applies to the X/Y flip compression.
In the worst case, up to four bytes may need to be read, if the buffer already
had two or three sets consumed, and the sequence needs 0xF of them:
0011[2233 44556677 8899aabb ccddeeff 00]112233

Tilemaps in the game's data where this happens:
07 0b 0c 16 18 19 24 26 29 37 39 3e 41 46 47 4a 4e 4f 50 53 54 67 7d

--------------------

Analyze: If encoding data that includes 00 values, how many 00 values in a row
         are needed to be worth it to split them off with their own type byte?
Try to minimize the number of times you have to split off high bit values into
their own dedicated bytes.

Analyzing this data with run length encoding should be a good start point.
From there, analyze the RLE tags to create a series of compression tags.
Each compression tag should include the position, the size, and how many "high
bit set" bytes are to be written after the type byte.

--------------------

For the case where you have a single non-zero value followed by many 00 values,
see if it could be better to temporarily limit the size of the 00 run now, and
split off the rest of the 00 run into its own type byte. Possible to prevent
having to split off the non-zero value into the "read as you go" buffers? Cases:

total | 1st run | 2nd run | Buffer? | Two-byte 2nd run?
01-08 | 01-08   |  -----  | No      | No
09-28 | 08      |  01-20  | No      | No
      | 09-28   |  -----  | Yes     | No
29-47 | 08      |  21-3F  | No      | No
      | 28      |  01-1F  | Yes     | No
48-67 | 08      |  40-5F  | No      | Yes
      | 28      |  20-3F  | Yes     | No
68-108| 08      |  60-100 | No      | Yes
      | 28      |  40-E0  | Yes     | Yes
109-28| 08 + 100 + 01-20  | No      | Yes, and 3rd run
      | 28      |  E1-100 | Yes     | Yes
129+  | Need 3+ blocks anyway, so limit the first run

Decisions:
 01- 08: Single run
 09- 28: Single run; 2 bits are better than 1 byte for 2nd run
 29- 47: Using 2nd run anyway, so limit 1st run to 8, rest in 2nd run
 48- 67: 1st run of 28, rest in 2nd run; 2 bits better than 1 byte for 2nd run
 68-108: 2nd run is 2 bytes anyway, so limit 1st run to 8, rest in 2nd run
109-128: 1st run of 28, rest in 2nd run; 2 bits better than 1 byte for 3rd run

Condense logic:
01-28, 48-67, 109-128: Fill the single run as much as you can
29-47, 68-108:         Limit 1st run to 8 bytes

Or in terms of code using named constants:
29-47:  HIGH_BITS_00_AFTER_VAL_LIMIT_28 < size <= RUN_00_THRESHOLD_3F +HIGH_BITS_00_AFTER_VAL_THRESHOLD_8
68-108: HIGH_BITS_00_AFTER_VAL_LIMIT_28 + RUN_00_THRESHOLD_3F < size <= RUN_00_LIMIT_100 + HIGH_BITS_00_AFTER_VAL_THRESHOLD_8

--------------------------------------------------------------------------------

Palette compression 

Need to keep track of:
- Palette value buffer (eight value array)
- Number of occupied values (0-7) in palette value buffer

00xx xxxx: $029CC7 (Range 00-3F -- 0x3F is a special case)
Purpose: Use palette 0 for up to 0x100 bytes.
- If 0x1 <= size <= 0x3F, encode (size-1) as the x bits.
- If 0x40 <= size <= 0x100, use type byte 0x7F; encode (size-1) in next byte.

0100 xxxx: $029CE7 (Range 40-4F)
Purpose: Reuse one palette value from one tile row up; next 0x1-0x10 vals are 0.
Encode (skip_size-1) in xxxx bits.

011p ppxx: $029CFC (Range 60-7F)
1010 xxxx: $029D06 (Range A0-AF)
Purpose: New palette value for one tile, then use palette 0 for 0x1-0x14 tiles.
- If skip size <= 0x4, use the 011p ppxx case.

Because the "extra data" buffer is 3 bytes instead of just 1 byte, it is very
important to try to utilize the space in the buffer as effectively as you can,
and only use the buffer as you go along if not using it would indeed be worse.

In isolation, it may be better to encode a run of length 2 as two literals,
because you're using two 3-bit values instead of one 8-bit value. However, if
you overuse this, it can unnecessarily produce a 3-byte buffer for you. So try
to only resort to this if there's a literal sequence right before or after it.

On one hand, if you have a sparsely used buffer like only 1 or 2 used entries,
you're mostly wasting the buffer space (18 or 21 empty bits).

Two ways to utilize the buffer space:
- If few values are filled in (1-4), you can try to see if you can convert some
  of the type bytes with the extra values to remove enough buffer values to
  prevent writing a 3 byte buffer (but using at most 2 extra type bytes so you
  actually save space over the buffer). For example, if you had combined a run
  of length 2 onto either end of a literal sequence, you can use an extra type
  byte to save 2 values.
- Alternately, you can (regardless of # values in last buffer) try to save type
  bytes by purposefully using more buffer values. For example, if you can fit 3+
  buffer values and find two consecutive [L=2 run of X] blocks, you can combine
  them into one block as [L=4 literals] to save a byte.

Try both and see if one saves more bytes than the other.

You can use the second option's logic to compressing the high bit and X/Y flip
blocks, but their buffer sizes are a more restrictive 4 values, instead of 8.

With ASM changes, you can improve the format.

From a space point of view for the ASM code, there is quite a lot of repeated
code that you can split off into JSRs to make space for improvements. Examples:
- load byte from pointer, advance pointer, bank wrap if needed
- Y <- start offset for tilemap, zero out the byte for # buffer values left,
  and check flag for whether the next data block is compressed
- reuse code between the palette and X/Y cases where applicable
  * write bits of value to buffer, advance pointer, decrement loop counter
  * ALL the code for "use 0 for N entries"
  * nearly all the code for "repeat new value N times"
- convert JMPs to BRAs if the branch distances allow for it
- store low nibble of type byte to $01, and also...
- X <- Y - 0x20; get offset to data from one row up

You can't do that with purely in-place edits, so obtain a disassembly of the
decompression code and edit it from there.

Five of the cases can require reading another byte after the type byte to get
the size of the block to decompress. Two for low bytes: increasing sequence of
length 0x40-0x100, and repeat new ID for 0x21-0x100 bytes (type bytes 7F, DF).
And one each for the three other phases: use 00 for 0x40-0x100 entries (3F).

Despite how these cases read an entire byte for the size, the full range of 256
values from it is not fully utilized. For example, using [00] for the type byte
for the "00 run" case is equivalent to using [3F 00]. The second byte only
becomes useful once it is in the range 0x3F-0xFF e.g. [3F 80].

To fix this, you can extend the ranges from 0x40-0x100 to 0x40-0x13F, and
similarly from 0x21-0x100 to 0x21-0x120. However, you need to be careful with
the M flag as you decode the size from the byte, write data to the buffer, and
check the loop counter.

Application: if you have a high bits block consisting of 0x380 00 values, you
can compress them with just three tags (13F + 13F + 102) instead of four tags
(100 + 100 + 100 + 80). It saves two bytes per block this happens with.

One disadvantage to the increasing sequence case for low bytes is that it will
only happen if the sequence's starting byte matches the current tile ID. This is
especially noticeable with the tilemap at $46C1B8 (2nd for bookmark screen).
At offset 0x7C, the current tile ID of 42 is followed by [00 00 00 44 ...] and
skips over tile ID 43, which doesn't appear until offset 0x160. In the meantime,
there are seven large groups of literals (sizes 0x1A+) that all contribute to
this compressed low bytes block being the largest at 0x245.

What if you could add a case to set the current tile ID to an arbitrary value?

First is the matter of what value to use for the type byte. One value should be
enough. Since literals were on the mind, I grep'd tilemap decompression logs I
generated for the Japanese game. The literals case allows for up to 0x20 bytes
at once, but the single largest groups of literals present in the data are 0x1E
(see offsets 0x100 and 0x2C1 in $46C1B8). We can sacrifice one byte of its range
(0x1-0x20 -> 0x1-0x1F) for the new case. Let's pick FF to be inobtrusive.

The ASM hack should be simple: if got FF, read a byte from the pointer, set as
current tile ID, and go back to start of the loop. So each instance of the case
will take 2 bytes in the compressed low bytes block.

Considerations regarding "is it worth it" in terms of space.
- The subsequent increasing sequence case will require another byte.
- You may or may not need to restore whatever the current tile ID would have
  been had you not changed the low byte. Expect a total cost of 4 bytes.
Let's compare a situation where we can apply this:
(N+1) N literals
- versus -
(2) set current tile ID
(1) increasing sequence, length N
(2) potentially set current tile ID
N must satisfy either 5 < N+1 or 3 < N+1. So N > 4 or N > 2.

Implementing this with N>2 across the board saved 0xF5 bytes with $46C1B8 alone.
More tilemaps shrunk as well, but a few got larger due to the change:

compressed data is now only 0x10 bytes (3 groups in tilemap 4B @ 330, 350, 370).
The data for those three groups are as below:

No literal blocks are size 0xC-0xE, and 13 blocks are size 0xB (9 in 4B).

Notice how these data blocks contain monotonically decreasing sequences of tile
IDs. From a graphics point of view, this could correspond to a tile row that
gets mirrored horizontally along some tile boundary.

Let's make a case for monotonically decreasing IDs to save space with these.
Assume that reusing from one row up would not help here.

We COULD use the 3 byte format described above as an alternate to the case for
setting the type byte, but there's a better option. Literal blocks are now at
most 0x10, so we can restrict their range again from 0x1-0x1F to 0x1-0x10 (type
byte range E0-EF). This frees up type byte range F0-FE (FF taken already).

Since a "decreasing sequence" of length 1 can be equivalently represented by a
literal, make the minimum length 2. So the range F0-FE corresponds to a length
range of 0x2-0x10. Tack on another byte to indicate the start tile ID, and we
can represent all of these decreasing sequences with just 2 bytes.

Icing on the cake, you can encode a two-byte decreasing sequence like [76 75] in
1 fewer byte than encoding as literals.

This turned out to be even more powerful than setting the current ID, saving
another 800 bytes. Dramatic examples include saving 119 bytes for tilemap 19,
205 for 4B, 219 total between maps 4D-57, another 68 for $46C1B8, and 91 for 7D.

The only place it outright compressed worse was tilemap 13 at 0x367.
The data is [21 20 ; E9 ; 03 02 ; 05]. It's better to encode this as one block
of literals (7) than as two decreasing sequences and two separate blocks of one
literal apiece (2*2 + 2*2 = 8). Insight is that if you have a literal and a
decreasing sequence of length 2 (or the other way around), you can absorb the
sequence into the literals and have the three values take up 4 bytes either way.

Implementing a fix for this also got me another 2 bytes back with tilemap 55. I
found this was at offset 0x2AD: [05 ; 11 10 ; 10 11 05 ; 11 10 ; 10 0F ; 04].
Either a literal block (0xC), or 3 decreasing sequences and three literal blocks
(2 + 2 + 4 + 2 + 2 + 2 = 0xE).

Another insight was that I had to explicitly prevent using a decreasing sequence
at some offset if an increasing sequence is possible there, even if only 1 byte
long. Not doing this wiped out most of the gains I described above.

Later, I put in a check that accounts for the possibility that the current byte
(start value of the decreasing sequence) does appear soon after the decreasing
sequence. Example: suppose current ID is 05 with the data [05 04 03 02 01 05].
- If you reject the decreasing sequence now in favor of the increasing sequence,
  you would compress as [1 inc seq] [4 dec seq] [1 lit].  1+2+2 = 5 bytes
- With new check, compress data as [5 dec seq] [1 inc seq]. 2+1 = 3 bytes
While it turned out there were no occurrences of this pattern in the Japanese
game's tilemap data, adding this new check did not harm compression, either.

If you make the minimum length 2, you can dedicate 2 bits of a type byte to the
remaining length, for a range of 2-5. You can fit this into the literals range
by reducing its size range from currently 0x1-0x10 to 0x1-0xC, and repurposing
the type byte range from EC-EF.

- You can apply the same insights with "combine isolated increasing sequence of
  length 2 and literal group" as with the decreasing sequence case.
- Something obvious to keep track of in the recompression code was making sure
  this case wouldn't happen if the current position has the current tile ID.
  The already existing case compresses data much better.
- Less obvious: if an isolated sequence CONTAINS the current tile ID, you must
  explicitly prevent this case. This popped up with gfx ID 6F @ 0x161.
  Curr tile ID = 8F, data: [8E 8F 90 91 92 ; 4E 4E 4E 4E ; 93 94]

  Also popped up with gfx ID 0F, saving 1 byte. I couldn't directly compare the
  two different compression logs, but I believe this was at 0x25A.
  Current tile ID E6, data: [E4 E5 E6 E7 ; 7E 7F ; 60 01 ; 73 ; E8 E9 EA EB ...]
  Better: [set E4]+[inc 4] [isol inc 2] [row up 2] [lit 1] [inc seq]
  Worse:  [isol inc 4] [isol inc 2] [row up 2] [lit 1] [set E8]+[inc seq]
  Compare: (2+1)+2+1+2+1 = 9, vs 2+2+1+2+(2+1) = 10

That last point came up because if you try to do too many of these isolated
sequences as opposed to setting the current ID, you get diminishing returns.
For example, if you can do three increasing sequences after setting the current
ID, you can compress them as [set] [inc] [inc] [inc] = 2 + 1*3 = 5, instead of
as [isol inc] [isol inc] [isol inc] = 2*3 = 6. Unfortunately, comparing these
cases will require lookahead and comparison.
